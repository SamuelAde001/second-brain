A pace timer for finishing an edit on a deadline. The user types three things into it: the full video length, where the playhead is now, and the finish-by time in WAT. It draws a straight line from their current position to the end of the timeline at the deadline, then shows every second where the playhead should be. They check in with their real position to see if they're ahead or behind, and re-anchor when they've fallen off the plan.

`assets/edit-clock.html` is the finished, tested clock. The job is almost always to hand it over, not to build it.

## Steps

1. **Copy the template to outputs and present it.**


   If the skill is installed somewhere else, use the `assets/` folder next to this file. Don't retype the HTML from memory. It's a long file that has been through several rounds of real use, and rewriting it burns a lot of output and tends to bring back bugs that were already fixed (see Design decisions).

2. **If the message includes the numbers, work out the pace.** When the user gives a length, position and deadline in chat, run:

   ```bash
   python3 00-System/skills/edit-clock/scripts/pace.py --length 33:46 --pos 10:53 --end 19:00
   ```

   Add `--now 14:48` only if they told you the current time; otherwise it uses the current WAT time. Put the pace and checkpoints in the reply so they know the target before the file is even open. Don't hardcode the numbers into the HTML: the setup form takes them, and hardcoded values are what forced a file rewrite every time the plan slipped in early versions.

3. **Reply short.** The user already knows the clock. Two or three sentences: enter the three numbers, check in as you go, re-anchor if you fall behind. Only explain something if it changed. No feature tour.

## Design decisions (don't regress these)

- **WAT is read directly** (the `WAT` constant, UTC+1), not the device clock, so the clock stays right even if the PC's timezone is set elsewhere. If the user is ever working from another timezone, change that constant.
- **The deadline is locked as an absolute timestamp at setup.** An earlier version recalculated it from today's date on every load, so a plan left over from a previous video reopened with a pace line stretched across days.
- **Stale plans clear themselves.** A saved plan more than 6 hours past its deadline is wiped on load, so the file opens straight to setup for the next video.
- **A finish-by time earlier than now means tomorrow**, so deadlines past midnight work.
- **Re-anchor to now** exists because the user once fell behind and the whole file had to be rewritten with a new start point. Re-anchoring redraws the line from their real position and keeps the deadline.
- **After a check-in, the rate box shows what's needed from the real position**, not from the original plan. That's the number that tells them whether to speed up or move the deadline.
- **Screen wake lock, mobile viewport tags and safe-area padding** are there because the clock sometimes runs on a phone.
