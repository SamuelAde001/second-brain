Two phases, run in order, with the user re-cutting between them. **Never start Phase 2 until the
user has sent back an updated SRT.** Phase 1's whole job is to change the cut, so a Phase 2
transcript built on the old subtitles is worthless.

## Phase 0 — always gather this first

Before any analysis, ask for files and context. Do not skip this even if an SRT is already attached.

**Files needed:**
1. **Subtitle export** (`.srt` / `.vtt`) of the *current* cut — required.
2. **Timeline XML** (FCP7 / `xmeml` export from Resolve) — strongly preferred. Without it you cannot
   check frame rate, flash frames, or timeline start timecode, and the EDL timecodes may land wrong.
3. **The client's written script**, if one exists — this is how you find beats that were scripted but
   never recorded.

**Context questions** — ask these as a short batch, not one at a time:
- Was the script followed closely, or is a lot of it freestyled?
- Is the video a single recording (e.g. one OBS capture of camera + screen), or are the screen
  recordings separate media that gets laid over later? *This changes the cut advice completely — see
  "Ripple safety" below.*
- Which version of any script section was actually used (e.g. "Hook V2")?
- Anything already known to be broken — bad audio regions, sections re-recorded, pickups pending?
- Roughly how long should the finished video be, and is it deadline-constrained?

Use `ask_user_input_v0` for the multiple-choice ones where it fits. Then state the assumptions you're
proceeding on and start Phase 1.

## Deliverable formats — settled decisions, don't re-litigate

- **Markers are delivered as an EDL, never as a colour-coded XML.** Resolve ignores
  `<labels><label2>` on FCP7 XML import, so clip colours do not survive. This has been tested. Give
  a marker EDL; import path is **Timeline → Import → Timeline Markers from EDL**.
- **The transcript is a `.docx`.** Don't ask docx vs plain text.
- Read `references/edl-format.md` before generating any EDL and `references/frame-math.md` before
  converting any time value.

## Phase 1 — the cut pass

Run `scripts/parse_srt.py` and `scripts/audit_xml.py` first, then `scripts/find_repeats.py`. Read
their output before forming any opinion. Then read the whole transcript top to bottom — the scripts
catch mechanical problems, but most of the real finds are editorial and only surface from reading.

### What to look for

**Mechanical (scripts find these):**
- **Flash frames** — clips ≤6 frames. A 1-frame clip is always an error.
- **Duplicated source** — a later clip pulling source that an earlier clip already used.
- **Gaps** on the video track.
- **Near-identical cues** — the same sentence delivered twice.

**Editorial (only reading finds these):**
- **Duplicate takes** — he said the same beat twice and both survived the cut. Verbatim repeats of a
  CTA line are the most common.
- **Misspeaks that invert meaning** — e.g. "you do *not* need the Grow. You need the Advanced"
  immediately before "just go with basic." These matter more than any redundancy.
- **Garbled audio.** A cue whose text is far too long for its duration, or that reads as word salad,
  means the audio there is broken. Check whether it sits mid-clip in the XML — if it does, it's the
  audio, not a caption sync artifact.
- **Loops** — the same instruction given, then re-given 20 seconds later with a different phrasing
  in between. Very common in screen-recorded walkthroughs.
- **Nth repetition** — count how many times an idea lands. "The back end is set up" four times in
  three minutes is a trim even though no two sentences match.
- **CTA density** — count every pitch. Five community plugs in a 34-minute video is a problem worth
  raising even if each one individually is fine.
- **Orphan promises** — "I'll show you that in a minute" with no payoff.
- **Stale editor notes** in the script that the recording made obsolete.
- **Missing scripted sections** — diff the script against the transcript. A scripted beat that was
  never recorded is the single highest-value thing to surface, because it needs a client pickup and
  has the longest lead time.
- **A-roll droughts** — long stretches with no talking-head break. Flag the span.

### Tiering

Sort every find into three tiers and say clearly which is which:

- **Tier A — cut it.** Duplicates, misspeaks, garbled audio, flash frames. Not judgement calls.
- **Tier B — recommended trim.** Redundancy and pacing. The user may well keep some; that's fine.
- **Tier C — their call / needs a decision.** Monetisation beats, client conversations, re-record
  asks, pacing flags that aren't cuts.

### Precision

Give **exact in and out points in mm:ss.ss**, taken from the SRT cue boundaries, not rounded. For
each cut, name the **join** — what the last words before the cut are and what the first words after
it are — so the user can hear whether it works before touching the timeline. Where a cut point
coincides with something structural (a repair-audio boundary, an existing cut), say so.

### Ripple safety

If the video is a **single recording** (one OBS capture), everything is linked to one source and
ripple deletes cannot desync anything. Say so — it's reassuring and it's true.

If the screen recordings are **separate media not yet in the timeline**, say the cuts must be made
*before* the screen layer goes down, or the ripple will desync the whole back half.

### Phase 1 output

1. A tiered list in chat, with timings, lengths, reasoning and joins. Lead with the two or three
   findings that change the most (a missing section, a meaning-inverting misspeak), then the tables.
2. A marker EDL via `scripts/make_edl.py`. Colours: Tier A = `ResolveColorRed`, flash frames =
   `ResolveColorFuchsia`, Tier B = `ResolveColorYellow`, Tier C = `ResolveColorBlue`, notes and
   re-record asks = `ResolveColorGreen`. Duration markers spanning each in/out. Put the full
   reasoning in the marker name so it reads in Resolve without the chat open.

Then **stop and wait** for the updated SRT (and ideally XML).

## Phase 2 — the transcript pass

When the updated files arrive, first verify the re-cut: check the new duration, confirm the timeline
still starts at the same timecode and frame rate, and check which of the Phase 1 items were actually
taken. Report that briefly and don't push back on the ones they kept.

### Chapters, not beats

Section the video into **major narrative areas**, typically **6 to 12** for a 20–40 minute video.
Chapters are things like "Building the store" or "Making the ads" — not "Installing the app" or
"Choosing a banner". If a chapter runs 9 minutes, that is correct and expected; do not subdivide it
to make the chapters more even. The client's own written script is usually the best guide to where
the real seams are.

Every chapter boundary must land exactly on a sentence start.

### Transcript rules

Read `references/transcript-spec.md` for the full formatting spec. The rules that matter most:

- **ALL CAPS** for all body text, headings and list items.
- **Flowing paragraphs**, roughly 400 characters each, breaking at natural pivots. Never one
  paragraph per sentence — it must read like a transcript, not a subtitle dump.
- **Timecodes appear once, in the chapter header.** Never per sentence, never per paragraph.
- **Body text is a single colour throughout.** Screen-recorded passages are *not* coloured.
- **Red notes** mark every A-roll ↔ screen-recording switch, with a short descriptor of what's on
  screen. Red notes also flag anything else the user should stop and look at: audio that belongs to
  something playing on screen rather than the speaker, lines too garbled to correct confidently.
- **Purple box** around any prompt the speaker reads out on screen.
- **Lists** — pull spoken lists into bullets (flat sets) or numbers (ordered / named examples), but
  **only in A-roll passages**. Never list out screen-recorded content; it's already on screen.
- **Do not add highlight boxes or inline emphasis for quotes, briefs, figures or statistics.** This
  was tried and rejected. Body text stays plain.
- Fix **only unambiguous** auto-caption errors — a garbled brand or tool name that's obvious from
  context or from the script. Leave ambiguous garbles verbatim and flag them with a red note. Never
  smooth phrasing, remove filler or fix the speaker's grammar.

Build with `scripts/build_transcript.js`. Always render to PDF and view at least three pages
(first, one with a note or box, one near the end) before delivering.

### Phase 2 output

1. The `.docx` transcript.
2. A **chapter marker EDL** via `scripts/make_edl.py`. Chapters only — no A-roll/screen markers, no
   sub-beats. Each chapter a different colour. **Contiguous by construction:** chapter 1 starts at
   the timeline's first frame, every chapter's out point is the next one's in point, and the last
   chapter runs to the final frame. The script asserts this; if an assertion fails, fix the
   boundaries rather than the assertion.
3. In chat: the chapter table with in/out timecodes, the caption fixes applied, and anything left
   verbatim that the user should verify by ear.

## Working style

- **Proceed with flagged assumptions.** Make a sensible call, say what you assumed, and keep going.
  Save clarifying questions for structural decisions where guessing wrong means rebuilding.
- **Respect phase boundaries.** Finish one phase completely; don't jump ahead.
- **Surface problems proactively.** Answer the literal question, then say what else you found.
- **Preserve the speaker's words.** This is a reformatting job, not a rewrite.
