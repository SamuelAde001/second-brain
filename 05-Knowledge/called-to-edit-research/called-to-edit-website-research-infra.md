# Website research: Infrastructure: domain, mailbox, sending, video, booking, analytics

Part of [[05-Knowledge/called-to-edit-research/called-to-edit-website-research|Called to Edit website research]] (2026-10-26).

Simplest robust setup: merge the two Netlify sites into one site at calledtoedit.com, with each offer on its own path (/webinar, /community, /academy, /mentorship, /resources). Use Netlify DNS so the bare domain is fast and SSL is automatic. Keep video, mail and booking on specialist services, called from Netlify Functions.
Merging beats both alternatives. A proxy rewrite (/community/* to the other site) only works inside one Netlify team, allows one hop and times out after 26 s. You also can't 301 the proxied site's .netlify.app address without causing a redirect loop. A subdomain splits cookies, Blobs, env vars and webhooks across two sites. Blobs belong to one site but can be read from another with siteID plus a token, so community data can be moved safely.
Before launch, check whether the Netlify team is on a legacy plan or the new credit plan. On the credit Free plan, every production deploy costs 15 of 300 monthly credits and bandwidth costs 20 credits per GB. When credits run out, every site is paused. Agents that deploy often would hit that limit; the Personal plan is USD 9 a month for 1,000 credits.
Free branded email: ImprovMX forwards samuel@ to the Gmail he already uses (free tier: 500 forwards a day). Gmail 'Send mail as' then sends through Brevo's or Resend's SMTP, which signs mail with calledtoedit.com's DKIM. Sending through Gmail's own servers fails DMARC alignment and can show 'on behalf of'. Zoho Free (no IMAP, select data centres only) and Google Workspace are the paid or real-mailbox upgrades.
Move customer emails off Apps Script. A personal Gmail account can only send to 100 recipients a day through it, which a webinar day can exceed. Brevo's free plan allows 300 a day, Resend's 100 a day (3,000 a month).
For paid recordings, use Bunny Stream: no encoding fees, a Lagos PoP, Africa delivery at USD 0.06/GB, and signed embed tokens. Mux is a strong alternative because its first 100,000 delivery minutes each month are free. YouTube unlisted and Google Drive can't stop link sharing.
No scheduler (Cal.com, Calendly, TidyCal, Google) takes Paystack or Flutterwave payments. Stripe in Nigeria routes to Paystack, so use pay first, then book: the Flutterwave webhook calls the Cal.com API to create a single-use private booking link.
Analytics: Umami Cloud free (one website, 100k events a month, fits a merged site), plus Microsoft Clarity, plus a server-side funnel log. Add Meta Pixel and Conversions API only when ads start, deduplicated by a shared event_id.
WebSearch's shared budget ran out mid-research. Vimeo pricing, Nigeria-specific Zoho and Google prices, Brevo's daily-cap details and Gmail's late-2025 enforcement changes could not be verified and are listed as open questions.

## Findings

- **a-netlify-billing:** Netlify accounts created on or after 2025-09-04 are on credit plans. Free is a hard 300 credits a month, and when they run out every project is paused with a 'Site not available' page. Legacy Free (teams created before 2025-09-04, no end date stated): 100 GB bandwidth (hard limit), 300 build minutes, 125k function invocations per site per month, 100 form submissions per site per month. - **a-domain-dns:** Netlify DNS supports all the email records needed and gets apex-primary performance right, but it does not support DNSSEC. Supported record types: A, AAAA, CAA, CNAME, MX, NS, SRV and TXT (TXT up to 255 characters, so a long 2048-bit DKIM key may need splitting or a 1024-bit key; Gmail accepts 1024 bits or more). Records for other services, such as mail, are hosted only while at least one Netlify site uses the domain. Netlify's docs say: 'With Netlify DNS, both apex and subdomain configurations perform equally well.' With external DNS, Netlify 'strongly recommend[s]' making www primary. External records: apex ALIAS/ANAME/flattened CNAME to apex-loadbalancer.netlify.com (or A 75.2.60.5), and www CNAME to <site>.netlify.app. Certificate failures come from leftover AAAA records, multiple apex A records, DNSSEC turned on at the registrar, or a CAA record that leaves out Let's Encrypt. Assigning the apex or www adds both. Cross-team DNS records arrived 2025-11-17. *(high, as of 2026-10-26)* Sources: https://docs.netlify.com/manage/domains/configure-domains/dns-records/ · https://docs.netlify.com/manage/domains/get-started-with-domains/ · https://docs.netlify.com/manage/domains/configure-domains/configure-external-dns/ · https://docs.netlify.com/manage/domains/troubleshooting/troubleshoot-ssl-and-https/ · https://www.netlify.com/changelog/tag/domains.md · https://support.google.com/a/answer/81126
- **a-netlify-app-redirects:** Once a custom domain is set, Netlify does not 301 the old *.netlify.app address. It only sends a canonical Link header, so old links need explicit host-level 301! rules. Syntax that Netlify staff have confirmed: https://calledtoedit.netlify.app/* https://calledtoedit.com/:splat 301! (use 301, not 200). Pitfall (my inference): a catch-all rule on a hostname that still receives webhooks will 301 POSTs to /.netlify/functions/*. List the old page paths explicitly instead, or update webhook URLs first. Unique deploy URLs stay reachable. *(medium, as of forum posts, undated; checked 2026-10-26)* Sources: https://answers.netlify.com/t/recommended-status-code-for-redirecting-netlify-subdomain-to-primary-domain/3198 · https://paramdeo.com/blog/restricting-netlifys-default-subdomain-for-security-and-seo · https://community.netlify.com/t/prevent-google-from-indexing-default-netlify-app-domain-when-using-a-custom-domain/29469
- **a-proxy-vs-merge:** Proxy rewrites between Netlify sites are limited: same team only, one hop, 26 s timeout, relative asset paths break, and HTTP-to-HTTPS redirects can fail on proxied paths. The docs recommend proxying to the target's .netlify.app address ('/x/* https://other.netlify.app/:splat 200'). Custom headers aren't applied to proxied content, and JWS-signed proxies don't work between Netlify sites. My inferences for Samuel's case: (1) the community site's root-relative calls to /.netlify/functions/* would hit the webinar site, so its functions would need custom paths under /community/; (2) you can't 301 calledtoeditcommunity.netlify.app while also proxying to it, because the proxy would loop; (3) cookies set on *.netlify.app can't be shared across subdomains because netlify.app is on the Public Suffix List, so community members would have to log in again whichever way the move is done. *(high, as of 2026-10-26)* Sources: https://docs.netlify.com/routing/redirects/rewrites-proxies/ · https://docs.netlify.com/build/functions/api.md

- **b-spf-dmarc-multi-sender:** A domain may publish only ONE SPF TXT record at the root, with at most 10 DNS lookups. ## Recommendations

- **Run one Netlify site at calledtoedit.com (merge the community site into the webinar site), with Netlify DNS and the bare domain as primary. Each offer is a folder: /webinar, /community, /academy, /mentorship, /resources.** Why: One site means one deploy, one env-var set, one Blobs namespace, one Flutterwave webhook endpoint, cookies on one origin and one analytics property. It avoids the proxy's same-team, one-hop and 26 s limits and the 301-versus-proxy loop. With Netlify DNS the bare domain performs as well as www, and SSL is automatic. Trade-offs: A one-off migration of community functions, Blobs data and OAuth, and community members log in again. No DNSSEC on Netlify DNS. If later you want Cloudflare Email Routing, R2 or DNSSEC, move DNS to Cloudflare: proxy off (grey cloud), flattened CNAME @ to apex-loadbalancer.netlify.com, and www as primary, as Netlify advises. Steps: 1) Confirm both sites are in the same Netlify team and note both site IDs. 2) Registrar: turn DNSSEC off. 3) On the webinar site, add calledtoedit.com, choose 'Set up Netlify DNS' and paste the 4 Netlify nameservers at the registrar. The certificate is issued automatically (www is added too). Delete any AAAA records, and if you add a CAA record, allow letsencrypt.org. 4) Agent job: copy the community pages into /community/. Move the community functions into netlify/functions with config.path under /community/api/* (or a community- prefix) and fix the front-end fetch URLs. Copy env vars site to site in the Netlify UI or CLI without printing secrets (Samuel handles the key values). Read the old site's Blobs with getStore({name, siteID:'<community site id>', token}) in a one-off copy function. 5) Renewal safety: remove the schedule from the old site's auto-renew function BEFORE enabling it on the merged site, so a member is never charged twice. 6) Test on a Deploy Preview (0 deploy credits), then deploy to production. 7) Discord Developer Portal > OAuth2 > Redirects: ADD https://calledtoedit.com/community/api/discord/callback (exact match) and keep the old URI until it is no longer used. 8) Flutterwave Settings > Webhooks: point to https://calledtoedit.com/api/flutterwave-webhook. Check the verif-hash header, re-verify each transaction by id, store the processed transaction ids in Blobs so retries are ignored, and route by tx_ref prefix (WEB-, COM-, ACAD-, MENT-, PROD-). Turn on retries. 9) Old hosts: on the community site, add explicit page rules only: '/community/* https://calledtoedit.com/community/:splat 301!' and '/ https://calledtoedit.com/community 301!'. Never use a '/*' catch-all, so old function and webhook URLs keep working until retired. On the merged site add 'https://calledtoedit.netlify.app/ https://calledtoedit.com/webinar 301!' plus explicit old page paths. 10) Update the bio links, email templates and Apps Script origin checks.
